# 妙舆管理控制台与商业化演进规划

> 制定：2026-09-05
> 状态：`ADMIN-0` 规划完成，尚未开发管理控制台
> 适用范围：单机自部署、团队私有部署、公开网站/SaaS 三种形态
> 本文是后续权限、路由、设置归属和管理界面的实施边界；未达到阶段门槛前，不因“功能放不下”继续向普通设置页堆叠管理员能力。

---

## 1. 结论

妙舆已经有 Flask 后端，当前缺少的是独立的**管理控制台（Admin Console）**，不是另一个“后端服务”。

当前决策：

1. **现在完成规划，暂不开发管理控制台 UI**。先固定权限、路由、数据归属和部署边界，避免后续商业化时重写全部设置接口。
2. **单机与团队版默认仍使用一个外部端口**。用户应用使用 `/`，管理控制台未来使用 `/admin/`，普通 API 使用 `/api/*`，管理 API 使用 `/api/admin/*`。
3. **端口不是安全边界**。真正的安全边界必须由服务端身份、角色、资源归属和审计共同建立；隐藏菜单、不同路径或不同端口都不能代替权限校验。
4. **自部署版不必立即建设庞大的运营后台**。先保留轻量管理员设置；只有出现多人、配额、任务运维或商业运营需求时，才进入 `ADMIN-1+`。
5. **公开商业网站必须建设管理控制面**。用户管理、租户隔离、平台密钥、额度、账单、审计、任务和内容治理不能继续混在普通设置页。
6. **Keenable 已接入普通分析搜索并成为第一外部补漏**。当前顺序为 `SearXNG → Keenable → Brave → Tavily`，未配置 Key 时自动跳过；雷达中仍只作为第 6 层条件补漏，不参与默认高频轮询。

---

## 2. 第一性原理：为什么要区分“设置页”和“管理控制台”

系统里存在三类完全不同的状态：

| 状态类型 | 归属 | 典型内容 | 影响范围 |
|---|---|---|---|
| 用户偏好 | 当前用户 | 显示、默认分析选项、个人通知、个人密码 | 只影响本人 |
| 工作区配置 | 部署管理员/团队管理员 | 搜索与 AI 服务商、信源、雷达策略、报告模板、共享配额 | 影响整个部署或租户 |
| 平台运营配置 | 平台超级管理员 | 用户/租户、平台密钥、套餐、账单、任务队列、审计、安全策略 | 影响所有用户和平台稳定性 |

当前设置页把后两类能力放在同一个页面，并且当前登录模型只有固定 `admin`。这对单机工具足够简单，但不能自然扩展为多人或商业网站。

区隔原则：

- **设置页回答“我如何使用产品”**；
- **管理控制台回答“这个部署/租户如何运行”**；
- **平台运营台回答“整个平台如何安全、稳定、可计费地运行”**。

界面区隔只是结果，服务端权限才是根本。即使普通用户手工请求 `/api/admin/*`，后端也必须拒绝。

## 3. 当前架构判断

当前实现是适合自部署 MVP 的单体形态：

```text
浏览器
  └─ :5000
      ├─ /                 单页前端
      ├─ /api/*            Flask API
      ├─ 后台线程           分析、监测、雷达
      └─ data/              SQLite、任务、报告、运行配置
```

已具备：

- Flask 后端与同源前端；
- 固定管理员账号、HttpOnly 会话和 Bearer 兼容鉴权；
- `/api/settings`、AI/搜索/信源/雷达配置接口；
- Key 脱敏返回、Docker 数据卷、基础限流和安全响应头。

尚不具备：

- 普通用户、管理员、平台运营员的角色区分；
- 用户、工作区、租户的数据归属字段；
- 持久化会话、MFA、找回密码和登录审计；
- 平台级 Key、用户 BYOK Key 与工作区 Key 的分层；
- 额度、账单、作业队列、失败重放和运营审计；
- 可支撑多实例并发的任务调度与数据库租约。

因此当前系统是“单管理员自部署应用”，还不是多用户 SaaS。不能只增加一个后台页面，就宣称完成商业化架构。

## 4. 是否需要单独端口

### 4.1 当前与自部署版：不需要

推荐：

```text
http://host:5000/          用户应用
http://host:5000/admin/    管理控制台
http://host:5000/api/*     用户/业务 API
http://host:5000/api/admin/* 管理 API
```

理由：

- 同源 Cookie、CSRF、CORS、TLS 和反向代理最简单；
- Docker/FNOS 只暴露一个端口，安装和升级成本最低；
- 用户无法仅凭知道 `/admin/` 地址获得权限，后端仍执行角色校验；
- 避免两个端口产生跨域、证书、移动端连接和反向代理配置问题。

### 4.2 公开商业网站：可以分域名，不必暴露多个公网端口

推荐外部形态：

```text
https://app.example.com      用户产品
https://admin.example.com    平台运营台
https://api.example.com      API（可选）
```

外部仍统一走 HTTPS 443，由反向代理转发到内部服务。内部是否使用不同端口是部署细节，不是产品或权限设计。

只有以下情况才考虑独立内部端口/服务：

- 管理台与用户站由不同团队、不同发布节奏维护；
- 管理台需要 VPN、Cloudflare Access、企业 SSO 或 IP 白名单；
- API 流量与运营查询需要独立扩缩容；
- 安全审计要求平台运营面与用户面做网络隔离。

禁止把“换一个端口”当作管理员鉴权。

## 5. 页面与能力区隔

### 5.1 用户端设置

只保留与当前用户直接相关的项目：

- 个人密码、安全会话和通知偏好；
- 默认分析选项、报告语言和下载偏好；
- 个人 API Key（仅在明确支持 BYOK 时）；
- 个人雷达主题及其通知规则；
- 个人用量和套餐展示。

### 5.2 部署/工作区管理控制台

自部署版和团队版共用：

- 搜索服务：SearXNG、Keenable、Brave、Tavily、调用顺序、预算和健康；
- 分析模型：服务商、模型候选、故障切换和消耗；
- 信息来源与雷达来源：RSS/Atom、Bridge、同步状态和错误；
- 任务与调度：正在运行、失败、冷却、手动重试和取消；
- 数据与存储：空间占用、保留期限、备份和恢复；
- 系统健康：版本、数据库、浏览器/PDF、最近错误和依赖状态；
- 安全：管理员密码、会话、访问策略和审计记录。

### 5.3 商业平台运营台

仅公开网站/SaaS 需要：

- 用户、租户、角色和封禁；
- 套餐、额度、账单和退款辅助；
- 平台级 API Key 和供应商成本；
- 全局任务队列、失败任务、滥用检测和内容治理；
- 审计、告警、系统容量、版本和发布状态；
- 客服只读视图与受控“代用户排查”，所有操作留痕。

普通设置页不得出现平台总 Key、其他用户信息、全局账单或全局任务。

## 6. 权限模型

### 6.1 自部署兼容阶段

保留当前 `admin`，但代码接口开始按能力命名，不继续默认“已登录即拥有一切”：

| 能力 | 说明 |
|---|---|
| `analysis.run` | 发起分析 |
| `report.read/export` | 查看和导出报告 |
| `radar.manage` | 管理自己的雷达主题 |
| `workspace.configure` | 修改搜索、模型和信源 |
| `system.operate` | 查看系统状态、重试任务和备份 |
| `platform.admin` | 用户、租户、账单和平台密钥 |

单机版 `admin` 可以拥有前五项；第六项在没有商业平台时不存在。

### 6.2 多用户阶段

最小角色：

- `member`：分析、报告和个人雷达；
- `workspace_admin`：成员 + 工作区配置、共享配额和信源；
- `operator`：系统健康和任务运维，不默认读取敏感报告内容；
- `platform_admin`：平台运营能力；
- `support_readonly`：只读诊断，访问必须审计。

每个业务表必须明确 `user_id` 或 `workspace_id`；不存在归属字段的数据不能直接开放给多用户。

## 7. API 与路由规划

```text
/api/auth/*                     登录、退出、会话
/api/me/*                       当前用户资料、偏好、个人 Key
/api/workspaces/:id/*           工作区资源
/api/analysis/*                 分析任务
/api/radar/*                    用户/工作区雷达
/api/admin/providers/*          搜索与 AI 服务商管理
/api/admin/sources/*            全局/工作区信源管理
/api/admin/jobs/*               任务、重试、取消和调度状态
/api/admin/storage/*            数据保留、备份和恢复
/api/admin/system/*             健康、版本、依赖和诊断
/api/platform/*                 SaaS 用户、租户、套餐、账单和审计
```

迁移原则：

1. 现有 `/api/settings` 暂时兼容，不立即破坏前端；
2. 新增高级能力只进入 `/api/admin/*`；
3. 后续将 `/api/settings` 拆成 `/api/me/preferences` 与 `/api/admin/providers` 等窄接口；
4. 每个写接口必须有权限、输入校验、审计和幂等边界；
5. API 响应永不返回完整密钥、密码、哈希或内部令牌。

## 8. 密钥与 Keenable 的归属

### 8.1 自部署版

允许管理员在管理控制台录入 Key，后端保存并脱敏展示；同时保留 `.env`/Docker Secret 作为部署注入方式。

优先级：

```text
部署环境 Secret > 后端加密配置 > 未配置
```

环境注入的 Key 在页面中只显示“由部署环境管理”，不允许页面覆盖或删除。

### 8.2 SaaS 版

- 平台购买的 Key：只允许平台运营台管理，普通用户不可见；
- 用户 BYOK：按用户或租户加密隔离，调用日志只能记录 Key ID 和掩码；
- 加密主密钥必须来自部署 Secret，不得与密文存放在同一个 SQLite/数据库字段中；
- 供应商请求记录组织、租户、用途和成本，但不得记录明文 Key。

### 8.3 Keenable 多 Key

Keenable 的已认证限流和免费额度按组织计算。多个同组织 Key 主要用于环境隔离、撤销和容灾，不能视为额度叠加。

后续 Key 池最小字段：

```text
provider、key_id、encrypted_secret、masked_suffix、scope、enabled、
priority、last_used_at、consecutive_failures、cooldown_until、created_at
```

状态处理：

- `401/403`：禁用当前 Key，要求管理员处理；
- `402`：组织额度耗尽，停止该 Provider，不轮换同组织 Key继续消耗；
- `429`：按组织级冷却处理，不通过轮换 Key 规避限流；
- `5xx/网络异常`：有限重试后切换 Provider；
- 日/月预算达到上限：停止调用并明确提示，不静默扣费。

### 8.4 Keenable 接入位置

普通分析搜索的目标顺序：

```text
SearXNG → Keenable → Brave → Tavily
```

当前上线与验收步骤是：

1. 已完成 Provider、设置页、脱敏回显和连接测试，未填写 Key 时不发请求；
2. 已提升为 SearXNG 后的第一外部补漏，并保留空结果/错误自动回退；
3. 使用固定中文新闻测试集验证命中率、发布时间完整率、P95 延迟、错误率和单位成本，不达标时按数据降级顺序；
4. 雷达仍放在第 6 层，只在手动扩大搜索、前五层异常或完整性检查时触发；
5. 雷达使用 `published_after`/`acquired_after` 缩小窗口并按 URL 去重，不用搜索接口代替 RSS 增量采集。

## 9. 三种产品场景的合理方案

| 场景 | 是否需要独立管理台 | 推荐部署 | 数据与权限 | 复杂度 |
|---|---|---|---|---|
| 个人/家庭自部署 | 暂不需要完整后台；设置页增加“高级管理”即可 | 单容器、单端口、SQLite | 单管理员、BYOK、本地数据 | 低 |
| 小团队/机构私有部署 | 需要工作区管理控制台 | 同域同端口起步，反向代理 HTTPS | 成员/管理员、共享配额、审计、备份 | 中 |
| 公开商业网站/SaaS | 必须有管理控制面 | 用户站与管理域名分离，内部可拆服务 | 多租户、RBAC、计费、平台 Key、审计和风控 | 高 |

自部署版建设完整 SaaS 后台会增加安装、维护和迁移成本，却没有对应收益；公开网站继续沿用单 `admin` 和共享 SQLite 则存在越权、数据混用、成本失控和无法追责的结构性风险。

## 10. 分阶段实施计划

### ADMIN-0：架构规划（当前阶段）

- 固定用户设置、工作区管理和平台运营三层边界；
- 固定同端口 `/admin/` 与 `/api/admin/*` 路由策略；
- 记录角色、密钥、数据归属和审计要求；
- 不开发页面、不迁移接口、不改变部署端口。

验收：本文与开发计划完成同步，后续新高级功能能够明确归属。

### ADMIN-1：单机管理能力收口

进入条件：雷达 `RADAR-SRC-1/2` 完成人工验收，Keenable 真实 Key 完成质量与条款验收。

- 将搜索、AI、信源、雷达来源归入“系统管理”；
- 增加服务健康、预算、最近错误和版本信息；
- 继续只有一个 `admin`；
- 使用同一端口和同一 Flask 应用；
- 不引入租户、账单或微服务。

### ADMIN-2：团队工作区

进入条件：出现真实的多人共享部署需求，而不是预想需求。

- 用户、工作区、成员和角色；
- 所有任务、报告、雷达、Key 增加归属；
- 会话持久化、邀请、重置密码、审计；
- 数据库评估迁移 PostgreSQL，任务调度评估独立 worker；
- 迁移必须提供单机数据升级与回滚方案。

### ADMIN-3：公开网站运营台

进入条件：明确对外注册、付费或大规模公共访问。

- 平台与租户双层 RBAC；
- 套餐、额度、计费台账、供应商成本和防滥用；
- 管理域名采用 MFA/SSO、Cloudflare Access 或等价保护；
- 平台任务队列、容量、告警、审计与内容治理；
- 管理台前端可以独立工程和发布，但仍通过受控 API 操作。

### ADMIN-4：服务拆分（按指标触发）

只有出现以下证据才拆服务/端口：

- 单进程任务队列持续拥塞；
- SQLite 写锁或数据规模成为实际瓶颈；
- 用户/API/后台运维需要独立扩缩容；
- 发布或安全要求必须网络隔离。

没有数据证明前，保持模块化单体，避免提前承担分布式系统成本。

## 11. 管理控制台信息架构草案

```text
管理控制台
├─ 概览
│  ├─ 服务健康
│  ├─ 今日任务/失败
│  ├─ API 消耗与预算
│  └─ 存储与版本
├─ 服务配置
│  ├─ 搜索服务（SearXNG/Keenable/Brave/Tavily）
│  ├─ 分析模型
│  └─ 调用策略
├─ 信源与雷达
│  ├─ 信息来源
│  ├─ RSS/Atom 与 Bridge
│  └─ 同步任务与健康
├─ 任务与报告
│  ├─ 运行中/失败任务
│  ├─ 重试/取消
│  └─ 数据保留
├─ 安全与审计
│  ├─ 管理员/成员
│  ├─ 会话与登录记录
│  └─ 操作审计
└─ 系统
   ├─ 备份恢复
   ├─ 依赖检查
   └─ 版本与升级
```

页面原则：健康与用量优先展示，配置表单按任务分组；密钥仅显示掩码；危险操作二次确认并写审计；不得把日志全文、栈信息或内部路径直接暴露给普通用户。

---

## 12. 硬边界与禁止事项

- 不以“独立端口”代替服务端角色校验；
- 不把管理菜单是否可见作为权限依据；
- 不在当前阶段引入第二套后端、微服务或复杂前端框架；
- 不把平台 API Key 暴露给浏览器或普通用户；
- 不允许不同用户共享无归属的任务、报告、雷达或密钥记录；
- 不在商业化前继续使用进程内会话作为最终方案；
- 不在没有预算上限时开放后台自动调用付费搜索；
- 不为了多 Key 轮换规避供应商组织级额度、限流或服务条款；
- 不在管理台提供任意命令执行、任意文件读取或原始数据库编辑能力。

---

## 13. 当前建议

现在保持现有产品开发节奏，先完成雷达 RSS/Atom 真实同步与 Keenable 真实 Key 的质量验证；同时以本文约束所有新增设置的归属。下一次真正开发管理界面时，从 `ADMIN-1` 的单机管理能力收口开始，继续使用一个端口，不直接跳到 SaaS 管理后台。

若确定开放公网注册或收费，则在开放前必须先完成 `ADMIN-2` 的用户/工作区/数据归属，再进入 `ADMIN-3`；不能先公开网站，再补租户隔离和权限。
