**协作规则：边做边更进度（增量落盘）**
- 每完成一个子步骤（非等整个任务收口）就同步更新本手册：§3 进度总表状态列、§4 待验证清单、§5 教训新增条目、§9 里程碑日志补一行。
- 一段工作告一段落（哪怕只是半项）立即提交并跑 `backend/sync_github.sh "提交说明"` 推 GitHub，确保远端与本地一致、新对话可随时接手。
- 更新口径：状态符号要反映真实状态（别把"刚写完代码"标 ✅✅）；教训写"现象→根因→对策"三要素，可复现的命令/数值一并记下；里程碑按日期追加，不覆写。
- 接手新对话的第一动作：读本文件 §3（进度总表）+ §4（待验证）+ 最近一次提交 `git log --oneline -5`，判断从哪续。
- **证据优先规则**：先落可追溯素材、来源等级、采集时间和可复跑状态，再生成结论；图表、Agent、自动告警都不能替代证据链。
- **渐进复杂度规则**：默认保持 Flask + SQLite + 纯 Python；只有监测量、并发或多用户需求用实测证明单机瓶颈后，才评估队列、向量库、微服务或复杂 Agent 框架。
- **外部能力接入规则**：每个新信源先记录条款/密钥/频率/字段/失败降级；每个新开源依赖先核许可证与安全更新，不直接复制实现。

## 1. 项目概览

**定位**：多信源舆情分析工具。`SearXNG/热榜/聚合 采集 → AI 四段式分析（事件概况/原因/风险/对策）→ 报告预览/编辑/导出`。参照知微事见的"态势面板"首页：打开即看当前热点、热度趋势、跨榜扩散。

**已具备功能（截至 v2.0）**：
- 采集：SearXNG 4 信源组 + tophub 6 热榜（官方 API 若可用）+ Buzzing JSON Feed + 相关性过滤（4-gram）+ 去重 + 三级可信度 + 媒体名识别 + S/A/B/C/D 信源等级
- 分析：AI 四章串行（事实→原因→风险→对策）、对策-风险 id 硬校验+顺序回填、媒体归属与权威事实约束、多源交叉验证标记（▲/◐）、来源链接可达性核查（D1）、媒体观点/网友观点分栏、AI 通道容灾（任务预检+服务商×模型双层故障转移+分级冷却+推理开关）
- 报告：网页四段式渲染 + 情感/信源/时间图表（ECharts 本地化）+ 代表性观点；在线编辑（改文→重生成 docx/md）；导出 docx/md/PDF
- 历史：任务/报告 SQLite 持久化、二级视图分页（每页 10）、同主题 ×N、文件页面内预览
- 首页：态势面板（榜单卡墙/跨榜扩散词/热度概览/趋势占位/一键分析）
- 部署：Dockerfile + GHCR + GitHub Actions 自动构建（推 main 即发新镜像）；飞牛 compose 部署验证通过
- 配置：设置页（左侧菜单：搜索服务/分析模型/信息来源），保存即生效（热重载）、Key 脱敏、AI 服务商注册表（内置品牌+自定义）；信息来源采用分类卡片预览，地址列表脱敏隐藏

**技术栈与约束**：
- 后端 Flask（纯 Python，无 C 扩展依赖——本机企业策略拦截 lxml/pydantic 等；Docker 内保持一致）
- 持久化 `sqlite3`（stdlib）；docx 生成 Node `docx`（backend/scripts/gen_docx.mjs，Node 20）
- 前端单文件无构建（frontend/index.html + 本地 ECharts vendor），墨色 token 体系（含暗色模式）
- 构建走 GitHub Actions（本机无 Docker）；`sync_github.sh` 一键同步（token 在本地 `.env` 的 GITHUB_PAT）

## 2. 架构与数据流

```
前端（单页）→ /api/* → Flask
  ├─ 任务：analyze → DB(tasks) → 后台线程 → pipeline
  │    pipeline: 配置热重载 → AI 预检 → 关键词扩展 → 采集(白名单标注) →
  │    四章 AI（facts含情感/观点/交叉验证 → 原因 → 风险 → 对策校验）→
  │    图表统计 + 链接核查(D1) → docx/md/json
  ├─ 信源：sources 表（81 条目录）→ tophubdata/HTML/轮替 provider
  ├─ 热榜：/api/hot/boards（六个固定公开榜位，NewsNow JSON → REBANG/TopHub HTML 降级）
  └─ 搜索：SearchRouter（SearXNG 主链路，Brave/Tavily 按配置故障切换或多源合并）
  └─ 设置：/api/settings（SQLite 覆盖 .env，热重载）/api/search/test（服务连通性）/api/sources（勾选/增删）
数据：data/（tasks 素材 / reports 报告三件套 / settings.db / hot_quota）
```

### 搜索 Provider 接入规则（2026-09-03）

分析任务的搜索服务统一经过 `backend/search_providers.py` 的 `SearchRouter`，现有 `SearXNG` 结果字段保持兼容，并新增 `provider` 字段用于证据追溯。首页热榜仍走 `hotlists.py`，不得把搜索结果当作平台热榜。

- 调用顺序固定为 `searxng,brave,tavily`；SearXNG 地址为空或外部服务没有填写 API Key 时自动跳过，不会阻塞后续 Provider。
- 设置页不开放顺序修改，只开放故障切换/多源合并策略；这样可以避免不同部署实例产生不可解释的结果差异。
- 默认策略为 `failover`：SearXNG 返回空结果或失败时，才调用下一个 Provider，避免用户填入 Key 后产生不必要费用。
- `fanout` 仅用于重点事件，会合并已配置 Provider 的结果；合并前按 URL 去重，不比较不同 Provider 的原生排序分数。
- Brave 使用官方 `GET /res/v1/web/search`，Key 放在 `X-Subscription-Token`，默认 `country=CN`、`search_lang=zh-hans`。
- Tavily 使用官方 `POST /search`，Key 放在 `Authorization: Bearer`，默认 `search_depth=basic`（1 credit），关闭 answer/raw content，按中国区域请求。
- API Key 只允许出现在 `.env` 或设置页提交请求中；`GET /api/settings` 只返回“已配置”与掩码，不返回明文；测试接口只读取后端已保存 Key。
- 401/403 不重试；429/5xx/超时由 Provider 返回错误，路由器进入下一个可用 Provider。三者都未配置时返回明确引导。后续再补充持久化健康度、冷却窗口和额度记账。

用户准备 API Key 后，在“设置 → 搜索服务”填写并保存，再点击对应 Provider 的“测试连接”。日常建议保持“故障切换（省额度）”；只有需要多源交叉检索时才选择“多源合并”。

## 5. 关键决策与教训（含本轮新增）

1. **热榜栅格预算**（2026-09-01）：`auto-fill + minmax` 按"能否放下 N 列"机械降级；榜单卡墙列宽 310px 在 585px 容器下差 51px 降单列。排查法：量容器实际宽度 → `列数=floor((容器+gap)/(列宽+gap))`。修复：列宽下限 272px。
2. **AI 服务商注册表兼容**（外部重构后）：`router/deepseek/qwen` 老 provider 名失效→ `_resolve` 增加 `router/local/custom` 别名映射到注册表自定义服务商，任务不再间歇降级。
3. **报告三件套时间戳同步**：长任务跨分钟导致 docx/json 不同名→统一 `ts` 一次取；`report["json"]` 在 dump 前赋值。
4. **信源语义：标注而非排除**：勾选=优先关注与等级标注；未勾选/名单外信源全部保留（信息完整性），权威性靠"事实只用 S/A"裁决，不靠物理排除。
5. **性能第一性**（已固化 README）：模型选型是最大速度杠杆（qwen 慢 3.8 倍）；并发触发 burst 429 负优化；流式更慢；空响应自动重试+降档；对策-风险 for_id 按序回填救误杀。
6. **视觉收敛**：优先复用既定设计系统（外部已有墨色 token+暗色），不另起炉灶；新增组件经 `--primary` 别名绑定主 token，杜绝硬编码色。
7. **运行环境红线**：本机无 Docker（构建走 Actions）、企业策略拦 C 扩展（保持纯 Python/Node/ECharts 本地）、改动前端注意浏览器缓存（index 已 no-store）。
9. **第三方数据通道必然腐烂定律**（2026-09-01 热榜复盘）：免费额度转售型 API（tophubdata 余额不足 100300）与私有接口约定（tophub.today nodeId 两步法）都没有 SLA，失效是必然、时间不定。对策不是找"更稳的单一源"，而是**多源轮替 + 当日缓存 + 静默降级**的结构性冗余；解析器优先选"页面服务端渲染的静态结构"（itemid 锚点直解），不依赖对方前端 JS 的二次接口。
10. **榜单墙按设备分治**（2026-09-02）：桌面把墙从 span7（≈585px，仅 2 列）升级为 span12 全宽 → 3 列，6 榜对称 2×3；平板自动 2 列；手机改为单列纵向阅读，避免横滑隐藏内容并保证 44px 触控热区。每榜最多 15 条，卡内纵向滚动，卡片高度稳定；趋势/概览/扩散三组件改等宽一行，消除旧 5fr/7fr 的 7/12 空白。
8. **UI 设计系统 v2 纪律**（2026-09-01，苹果式收敛）：字号只用整数阶梯（12/13/14/15/17/20），禁止 12.5/13.5 小数档；表单节奏走 4pt 网格、禁止负边距补偿；UI 结构内禁用 emoji（一律单色 SVG，viewBox 24 / stroke 1.8）；暗色模式只经 token 换色，组件内不得出现字面量色值（品牌色块 .lvl-*/.plogo 除外）。
11. **AI 通道 502 全链路诊断**（2026-09-01）：表面错误"fetch connect timeout (reset after 30s)"是 9router→上游连接超时的透传，根因三层叠加：① `amd/` 模型上游断连（通道级，换模型无效，只能换通道）；② **混合推理模型的 reasoning_tokens 计入 max_tokens 预算**——小预算请求全被推理吃光返回 200+空内容（预检预算 ≤32 必误判"通道故障"），大预算也侵蚀内容额度；`enable_thinking: false`（顶层参数，网关识别）根治，单章 260s+失败 → 13s 成功；③ facts 第 1 档全量大 prompt 在抖动网关更易 502（降档小 prompt 是有效逃生门，降档重试不得被"配置错误"判断拦截）。**对策（借鉴 LiteLLM 57.7k★ router）**：任务预检快速失败（不拖采集）+ 服务商链 × 每服务商模型候选表（`fallback_models` 落 settings.db）双层故障转移 + 分级冷却（鉴权错误 60 分钟 / 抖动类连续 2 次失败才冷却 5 分钟，给降档与下一章节留重试机会）+ 5xx 重试 2 次(5s) / 429 重试 3 次(2s/5s/10s)。陷阱：聚合多服务商错误消息含"缺少 API key"子串，下游不可用子串判断配置错误。
12. **搜索 Provider 先省额度再扩覆盖**（2026-09-03）：Brave/Tavily 不能简单与 SearXNG 做盲目轮询；默认 `failover` 只在主源空结果/失败时调用备用，`fanout` 由用户针对重点事件显式开启。所有结果保留 `provider` 字段，去重只按 URL/标题，不比较不同 Provider 的原生排序分数；API Key 通过设置页脱敏保存，测试接口不接收明文 Key。
12. **报告段落格式统一**（2026-09-01）：对策原始点（title/body/for_id）曾直接入 sections，渲染器读 `lead` 键 → 句首空白；一切段落经 `_points_to_paragraphs` 转 `{lead, body}`（for_id 透传），前端/docx/md 三渲染器只认这一种结构。
13. **视觉仿站的正确姿势**（2026-09-01，U3）：仿参考站（top.open2hub 热榜）不抄组件抄"设计语言"——提炼为四件事：①暗色主视觉深海军黑（#0b0e13）+ 表面明度差建层级、扁平无阴影（`--shadow-card: none`），描边退到 7% 白；②胶囊导航组（半透明容器 + 圆角 99 + 选中亮填充）；③榜卡 TOP3 暖色阶梯（红→橙→金，走 --hot-h/--hot-m/--warn token，两态自适应）；④控件节奏统一（搜索/发起条 44px 高 + r-md 圆角，9px 圆角全量归一到阶梯）。改动全部走 token，无新硬编码色；小屏导航防溢出策略：藏 logo 与图标、留文字（比缩放文字可读性好）。
14. **长字符串溢出表格的第一性修复**（2026-09-01）：长 URL 无断点，`table-layout: auto` 下 cell 的 min-content = 整串长度 → 表格撑破 `width:100%` 容器（实测附录单元格 1526px）。正解不是锁表格（`fixed` 会破坏标签列比例），而是给**断行许可**：`.report { overflow-wrap: anywhere }`——仅在将溢出时才允许任意字符处断行，URL 可断后 min-content 回落，表格自动收回容器内；对正常中英文折行零副作用。同类问题（观点脚注长链接）一并兜底。
15. **暗色字体"显示不清楚"的双杠杆修复**（2026-09-01）：深色模式下小字发淡 ≠ 玄学，是两个可量化因素的叠加。①**对比度**：U3 把暗色底压到 #0b0e13 的同时若把次要文字也调暗，12px 档对比度会跌破 WCAG 4.5:1（实测 --text-3 #6f7785 仅 4.28:1，主文字 16:1 所以"只有字看不清"）→ 提亮 --text-3 至 #8b96a6（6.45:1）、--text-2 至 #aeb6c4、--text 至 #eef1f6；②**小字字重**：暗底浅字在 400 细字重下笔画感知淡，12px 档辅助文本（f-help/task-meta/bw-cnt/q-src/radar-board/appendix 等）在暗色模式统一提至 500。改 token 不改布局，两态都验证。

16. **报告体验 P1 三件套**（2026-09-02～09-04）：①PDF 已从 html2canvas+jsPDF 截图链路切换为 Node Playwright + Chromium 原生 `page.pdf()`；前端把已排版报告 HTML、设计系统 CSS 和 ECharts SVG/PNG 提交给 `/api/report/export-pdf`，Flask 调用 `backend/scripts/render_pdf.mjs` 返回 PDF；②Word 含图表仍由图表 PNG dataURL→后端嵌入；③编辑快照/还原仍使用 `.bak.json` 与 `/api/report/restore`。
17. **PDF 光栅化根因**（2026-09-04）：报告 DOM 在浏览器中可见，临时黑色探针也可见，但 html2canvas 生成的 2 个 JPEG 均为纯白，说明其链路返回了“成功但无效”的结果。改用 Playwright 后，最小 HTML、Flask 集成和真实报告导出均生成结构完整 PDF。
18. **Windows Playwright 启动兼容**（2026-09-04）：本机应用控制策略阻止 Playwright 默认 headless-shell（`spawn UNKNOWN`），完整 Chrome 可正常启动。渲染脚本支持 `MIAOYU_CHROMIUM_PATH`，并自动探测常见 Chrome 安装路径；其他机器应在部署文档中明确安装 Chromium/Chrome。
19. **PDF 分页不可拆分原则**（2026-09-04）：`page-break-inside: avoid` 只放在章节外层时，章节一旦超过剩余页高，浏览器仍可能拆开内部段落、观点卡或图表。修复为章节允许跨页，但段落、观点卡、图表/图片、附录表格行分别使用 `break-inside: avoid`，并设置 `orphans/widows`；这样尽量保持完整阅读单元，超长单段仍可自然跨页，不制造空白页。
20. **屏幕布局与打印布局分离**（2026-09-04）：屏幕端三列图表在 PDF 中不能直接改成单列宽卡片，否则 SVG 仍沿用屏幕尺寸，造成图形偏左、标签拥挤和大面积空白。打印端保留 A4 三列仪表盘（`minmax(0, 1fr)` + 固定图表高度），观点卡另行单列，分别满足“信息密度”和“内容不可拆分”两个目标。

## 6. 性能与稳定性知识库（复盘专用，勿推翻）

- 单章生成 15s-2min（模型决定）；完整分析 3-5 分钟正常；小请求 >10s 表示网关忙
- 429 两类：burst（退避重试有效）/ quota exceeded（充值或换模型，当日暂停官方）
- 空内容响应：3s/6s 退避重试 + 素材减半降档；错误详情透传前端进度
- tophubdata 配额：1000 次/天，首页用聚合 `/hot` 1 次/刷新，业务错误当日暂停，900 阈值降级 HTML
- 舆情雷达平台偏科（2026-09-03）：雷达把六榜新标题合成一个数组，再按各平台不可比的 `hot` 数值全局排序并截取前 10；知乎有可解析热度、其他平台热度常为空，导致结果被知乎占满。修复为优先使用后端按榜单快照计算的 `is_new`，旧接口按榜单隔离快照，并以平台轮询交错展示，避免单一来源垄断。
- 热度标注统一（2026-09-03）：参考 [NewsNow 的 `extra.info` 展示约定](https://github.com/ourongxing/newsnow/blob/main/src/components/column/card.tsx)，六个平台主界面均按当前榜内位置显示“高热/中热/在榜”；来源原生热度仍保留在 `hot`/`heat.raw` 和提示语中，仅作追溯参考。`heat` 使用 `basis=rank`、`level=high|medium|listed`、`relative_score`、`tooltip`，不宣称跨平台绝对热度可比。
