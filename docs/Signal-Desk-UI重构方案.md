# Signal Desk UI 重构方案（v1.1）

> 方向：已选方案 1 ｜ 设置页采用左侧功能区 ｜ 制定：2026-09-02 ｜ 更新：2026-09-03 ｜ 状态：本地实现完成，移动端已验收，桌面宽屏待用户确认

## 1. 第一性原理

这个产品的核心价值不是“展示更多榜单”，而是帮助分析人员回答一个问题：**现在什么事情值得研判，我能否用可信证据快速形成判断？**

因此界面遵循这条注意力路径：

```text
发现值得关注的变化 → 输入主题 → 发起一次研判 → 查看证据与报告 → 回到历史继续工作
```

每个页面只服务一个主任务。榜单、统计、配置等内容必须为主任务提供证据或控制，不能与主任务争夺第一视觉层级。

## 2. 设计原则

- **目的**：首页第一屏明确展示“开始一次研判”，不以功能数量作为信息层级。
- **简洁**：六个热榜由重复卡片收敛为一个热点主叙事和一条来源带；完整榜单仍可通过分析入口访问。
- **清晰**：使用字号、留白、分组和细分隔线建立层级，少用边框和阴影。
- **Agency**：用户可以从主题、热点、历史三处进入同一个分析流程，并能返回、重试和继续查看。
- **可信**：来源数量、更新时间、可信等级和待核状态紧邻内容出现，不把“热度”伪装成“事实”。
- **Craft**：统一 4px 间距节奏、系统中文字体、可见焦点、至少 44px 触控目标，减少无意义动效。
- **无框优先**：不把每个信息块画成边框。默认用留白、字号和表面色差分组；只有会影响列表扫读的地方才使用极浅分隔线。

## 3. 页面职责与保留接口

| 页面 | 新职责 | 保留的现有能力/API |
|---|---|---|
| 态势 | 发现升温事件，并快速发起研判 | `/api/hot/boards`、`/api/analyze`、热点原文跳转、雷达与热度统计 |
| 分析 | 配置一次分析、观察进度、阅读/编辑/导出报告 | `/api/analyze`、`/api/tasks/<id>`、报告渲染、Word/PDF、编辑还原 |
| 历史 | 按时间找到任务和报告，继续查看 | `/api/tasks`、`/api/reports`、分页、报告预览 |
| 设置 | 管理采集实例、AI 服务商和信源目录 | `/api/settings`、`/api/ai/*`、`/api/sources/*` |

本轮只改变前端呈现和导航组织，不修改后端接口协议。未来 G1 接入时，新增 `scan_run_id`、来源健康度、证据数量等字段可以直接填入现有的状态/统计槽位。

## 4. 目标布局

### 4.1 首页

1. 顶栏：品牌、态势/分析/历史/设置、服务健康状态。
2. 页面标题：一句产品价值说明。
3. 主输入：`你要追踪什么？` + `开始研判`，错误和空状态紧邻输入框。
4. 升温事件：热度、变化率、来源数量、可信度、关键证据。
5. 来源带：微博、知乎、B站、百度、抖音、头条作为轻量来源入口。
6. 雷达和热度概览：作为次级证据区，必要时展开。

### 4.2 分析

- 页面头只回答“这页用来做什么”；主输入条固定在第一工作区，只有一个暖红色主动作“开始研判”。
- 服务商、事实校验轮属于同一输入条内的次级选项，不与主动作争夺视觉权重。
- 运行中按准备、关键词、采集、AI、报告阶段反馈；不显示无法观测的模型生成字数。
- 报告完成后，导出和编辑操作靠近报告标题；正文保持舒适阅读宽度，事实、观点、待核信息用语义色与留白区分，不用重边框堆叠。

### 4.3 历史

- 标题区只保留工作记录说明和返回态势入口；总量作为弱化辅助信息，不做大指标。
- 任务列表是主要内容，使用一张连续列表承载状态、主题、时间和“查看报告”，按行分隔而不是重复小卡片。
- 报告文件作为次级列表，使用更轻的标题与操作样式，避免与任务记录抢层级。
- 行内操作统一沿用暖红主动作、浅灰次动作和 `完成 / 进行中 / 失败` 三类状态语义；未来可接入搜索、时间范围和状态过滤，但当前不虚构接口返回值。

### 4.4 设置

- 仍保留“基本设置 / AI 接口 / 信源采集”三个面板，但把它们明确放入设置页左侧功能区；右侧只呈现当前面板内容。
- 左侧功能区使用低对比度表面色、单一暖红选中态和固定 44px 触控行，不使用第二套顶部 Tab，避免与全局导航重复。
- AI 接口面板内部的服务商列表仍可使用“列表 → 编辑”二级结构；它属于 AI 配置内容，不替代设置页一级功能区。
- 移动端将左侧功能区折叠为横向滚动分段控件；表单单列化，主按钮全宽，API Key 继续使用密码框、显示/隐藏按钮和“不回传明文”约束。

### 4.5 页面家族与组件契约

四个页面共享同一套页面壳层：顶部全局导航、页面眉标、32px 页面标题、15px 说明文字、18px 内容表面、暖红主动作和低对比度辅助状态。页面差异只来自任务对象，不来自另一套颜色或卡片语言。

| 层级 | 统一规则 | 禁止事项 |
|---|---|---|
| 全局 | 顶部只承载首页 / 分析 / 历史 / 设置；当前项使用暖红底线 | 页面内部再复制一套全局导航 |
| 页面头 | `page-kicker → h2 → p`，一句话说明主任务 | 把总数、服务商、更新时间做成大标题 |
| 内容区 | 留白、对齐、字号和表面色差优先；必要时使用极浅分隔线 | 每个字段或列表行都画边框、卡片套卡片 |
| 状态 | `running / done / error / pending` 对应统一徽标与文字 | 用颜色代替文字状态，或虚构缺失数据 |
| 交互 | 主动作暖红、次动作浅灰或文字、触控目标不小于 44px | 在不同页面重新定义按钮尺寸和语义 |

设置页左侧功能区是本轮确认的结构决策：桌面端用于降低三个设置面板的认知切换成本，移动端退化为横向分段而不占用纵向空间。功能区切换仍由现有 `data-panel` 和 `showPanel()` 驱动，并通过 `aria-current` 标识当前面板；后续新增“监测任务 / 报告模板 / 安全”等设置项时，只追加面板和菜单项，不改变接口协议。

## 5. 移动端规则

- 断点：`760px` 以内单列；`520px` 以内进入紧凑手机布局。
- 顶栏允许横向滚动或压缩为四个文字入口，禁止导航溢出视口。
- 主输入垂直排列，主按钮占满可用宽度，触控高度不低于 44px。
- 升温事件与证据栏先后排列；来源带横向滚动，避免六项挤压成不可读小字。
- 雷达/热度概览默认为折叠或次级区域；报告表格允许横向滚动，长 URL 可断行。
- 设置表单单列化，按钮与帮助文案分行；AI 服务商列表与编辑面板上下排列。
- 动效只用于状态变化；遵守 `prefers-reduced-motion`。

## 6. 分阶段实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| UI-1 | token、顶栏、首页主路径、升温事件和来源带 | 桌面首屏只有一个主 CTA，首页可从主题和热点发起分析 |
| UI-2 | 分析页层级、运行状态、报告阅读区 | 成功/失败/空报告三类状态可读，接口调用不变 |
| UI-3 | 历史与设置统一页面头、列表和表单节奏 | 桌面无过密卡片；移动端无横向溢出 |
| UI-4 | 浏览器视觉 QA、键盘焦点、暗/亮策略、动效收口 | 1440、1024、390 三种视口通过；控制台无新增错误 |

### 6.1 本次执行批次（UI-2 / UI-3 收口）

1. **先固化页面契约**：保持图一的顶栏与页面头，明确分析、历史、设置各自唯一主任务。
2. **再收口分析页**：输入条、进度、报告预览、最近任务沿用同一表面、间距和动作层级。
3. **再收口历史页**：任务列表作为主内容，报告文件降级为次级内容，避免重复统计卡。
4. **调整设置页**：桌面端一级功能区固定在左侧，右侧呈现当前面板；移动端改为横向分段。
5. **保留接口槽位**：只复用已有 API 和 DOM 槽位，不在没有后端字段时显示虚假指标；完成后执行桌面 / 移动端视觉与交互回归。
6. **细节打磨**：按效果图校准设置外壳、左侧栏内边距、内容标题比例、保存动作尺寸与移动端滚动条；设置菜单图标标记为装饰元素，避免干扰读屏顺序。

本批次交付不包含：新增监测 API、改变鉴权策略、改变热度算法、增加付费数据源或推送 GitHub。上述内容仍按 G1-G4 路线单独排期。

## 7. 后续接口槽位

前端为以下 G1 字段预留展示位置，但当前没有虚构数据：

- `scan_run_id`：分析进度和历史任务的内部追踪标识；
- `source_count`、`evidence_count`、`source_health`：升温事件和报告摘要；
- `published_at`、`captured_at`、`time_window`：时间线和热度变化说明；
- `confidence`、`evidence_ids`、`verification_status`：事实与推断分层；
- `trend_delta`、`baseline`、`alert_status`：未来持续监测与告警。

舆情雷达的选取规则：服务端 `is_new` 是按榜单快照计算的首选字段；兼容旧 API 时使用带 `source_id` 的榜单级本地快照。展示采用平台轮询交错，最多 10 条，不把不同平台的原始热度值放在同一排序轴上。热度标注统一按榜内位置计算：接口返回 `heat.basis=rank`、`heat.level`、`heat.relative_score` 和 `heat.tooltip`，主显示固定为“高热/中热/在榜”；来源原生值保留在 `heat.raw` 供追溯，不改变评价体系、不制造跨平台绝对分数。

这些字段缺失时组件必须隐藏或显示“暂无数据”，不能用热度条目数量冒充证据可信度。

### 7.1 页面与接口映射

| 页面区域 | 当前数据入口 | 当前展示 | 后续可接入槽位 |
|---|---|---|---|
| 分析输入 / 进度 | `POST /api/analyze`、`GET /api/tasks/<id>` | 主题、阶段、成功/失败状态 | `scan_run_id`、阶段耗时、`source_health` |
| 分析报告 | 任务结果、报告渲染接口 | 事实 / 原因 / 风险 / 对策、证据与导出 | `evidence_ids`、`confidence`、`verification_status` |
| 历史任务 | `GET /api/tasks?page&per` | 状态、主题、创建时间、报告入口 | `time_window`、`trend_delta`、状态与主题过滤 |
| 历史文件 | `GET /api/reports/list`、`GET /api/reports/<name>` | 页面内预览、下载 | 报告版本、来源快照、生成任务关联 |
| 基本设置 | `GET/POST /api/settings` | SearXNG 地址、保存即生效 | 配置校验结果、最近生效时间 |
| AI 接口 | `/api/ai/providers`、`/api/settings` | 服务商列表、脱敏 Key、测试和启用 | `provider_health`、冷却状态、轮询顺序 |
| 信源采集 | `/api/sources`、`/api/sources/toggle` | 分组、可信等级、启停和手动添加 | `source_health`、最近采集、失败原因 |

接口原则：页面只消费后端已确认的字段；缺失字段隐藏或显示“暂无数据”，不把条目数、榜内排名或模型配置状态包装成“可信度”。
