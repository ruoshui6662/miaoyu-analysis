> 状态：`RADAR-SRC-1` 后端基线开发中，管理 UI 尚未开始
> 版本：v1.1
> 更新：2026-09-05

> 优先级：本文件是雷达信源管理的唯一专项基线；与通用雷达规划冲突时，以本文件更严格的约束为准。

## 1. 目标与第一性原理

雷达必须持续回答：**从用户明确配置的公开来源中，最近出现了哪些包含目标关键词的新内容？**

实现必须围绕四个相互独立的对象展开：

1. **来源身份**：内容由谁发布，例如新华社、某政府机构或某公共账号；
2. **采集端点**：系统从哪里读取，例如 RSS 地址、栏目页、RSSHub 路由或官方 API；
3. **主题绑定**：哪些端点参与某个关键词主题；
4. **同步状态**：端点何时检查、是否成功、下次何时运行以及游标推进到哪里。

不得继续把上述四类信息混入一个 URL 字段或 `extra` JSON 后直接调度。用户增加关键词不应增加外部信源请求次数；用户增加来源才会增加对应端点的轮询任务。

### 1.1 产品边界

- “信息来源”负责来源身份、可信等级和分析范围；
- “雷达管理”负责可执行的采集端点、同步频率、健康状态和主题绑定；
- “雷达”页面负责关键词与时间线，不承担复杂信源配置；
- 一条来源身份可以关联多个采集端点；
- 一个端点可以服务多个关键词主题，但每轮只能抓取一次；
- 雷达只记录标题、链接、摘要、发布时间、发现时间和命中词，不自动生成分析结论。

## 2. 严格开发方向

### 2.1 必须按以下顺序实施

1. RSS/Atom 数据模型、解析器和条件请求；
2. 雷达信源 CRUD、检测接口、健康状态和设置页管理界面；
3. 主题与端点绑定、单源单抓和本地多主题分发；
4. 网站 Feed 自动发现；
5. RSSHub/RSS-Bridge 与公共账号适配；
6. 安全、并发租约、退避、可观测性和 24 小时稳定性验收；
7. 只有前六项验收通过后，才评估 SearXNG/GDELT/付费搜索补漏。

后续阶段不得提前侵入当前阶段。任何绕过顺序的实现必须先修改本规范、记录原因和回滚方案，并经人工确认。

### 2.2 明确禁止

1. 不把 Playwright/Chromium 作为普通网站的默认定时抓取器；
2. 不绕过登录、验证码、反爬、robots 约束或付费墙；
3. 不要求用户提交平台账号密码、个人 Cookie 或浏览器会话；
4. 不默认抓取需要登录的私域内容；
5. 不把网站首页 URL 直接当作可解析 Feed；
6. 不按“关键词 × 来源”重复请求；
7. 不因标题相似而删除底层证据；
8. 不在后台静默调用 Brave/Tavily 或产生付费请求；
9. 不在 MVP 引入 Redis、Celery、Kafka、Elasticsearch、向量数据库或独立微服务；
10. 不让信源失败阻塞其他来源、分析功能或应用启动；
11. 不删除来源时级联删除已采集的历史 Mention；
12. 不使用 AI 判断内容是否与关键词相关，基础匹配必须可解释、可复现。

## 3. 支持类型与接入优先级

| 类型 | 用户输入 | 系统行为 | 默认状态 |
|---|---|---|---|
| RSS/Atom | Feed URL | 校验、预览、条件请求、增量解析 | 第一阶段启用 |
| 网站 | 官网或栏目 URL | 只做 Feed 自动发现；没有 Feed 时要求选择受控适配方式 | 第二阶段启用 |
| RSSHub/RSS-Bridge | 实例地址与路由 | 视为结构化 Feed，并单独标记外部适配来源 | 第三阶段可选 |
| 公共账号 | 平台、主页 URL 或公开标识 | 映射到官方 Feed、官方 API 或已配置 Bridge | 第三阶段按平台启用 |
| 官方 API | API 地址与后端密钥引用 | 仅为有稳定公开接口的平台建立专用 Adapter | 按需启用 |
| 搜索补漏 | 关键词主题 | 低频执行，不属于用户自定义信源 | 六层架构后续阶段 |

### 3.1 网站输入的处理规则

用户添加网站时必须先执行发现流程：

1. 规范化并安全校验 URL；
2. 获取页面头部并查找 `rel="alternate"` 的 RSS/Atom 声明；
3. 尝试受控的常见 Feed 路径；
4. 展示发现结果、Feed 标题和最近条目供用户确认；
5. 没有 Feed 时，不得自动进入通用 HTML 深度抓取；
6. 只能提示用户选择 RSSHub/RSS-Bridge、已注册站点适配器或 SearXNG 低频补漏。

### 3.2 公共账号的处理规则

- 只接入公开可访问账号；
- 优先级固定为官方 Feed → 官方 API → 管理员配置的 RSSHub/RSS-Bridge → 不支持；
- 每个平台必须有独立 Adapter 和测试夹具，不建立“万能账号抓取器”；
- 不支持的平台必须明确显示“不支持”，不能伪装为已订阅；
- API Token 只能使用后端密钥引用，不能写入 URL、前端状态或日志。

## 4. 数据模型规范

### 4.1 `sources`：来源身份

继续复用现有 `sources`，仅表达发布主体及其可信属性：

```text
id / name / host / category / level / enabled / manual / sort
```

`sources` 不直接保存同步游标，不用一个 `host` 同时表达 RSS、账号和 API。

### 4.2 新增 `source_endpoints`：采集端点

```text
id                    INTEGER PRIMARY KEY
source_id             INTEGER NOT NULL
endpoint_type         TEXT NOT NULL
url                   TEXT NOT NULL
platform              TEXT DEFAULT ''
account_identifier    TEXT DEFAULT ''
adapter_key           TEXT DEFAULT ''
auth_ref              TEXT DEFAULT ''
poll_interval_seconds INTEGER NOT NULL DEFAULT 900
enabled               INTEGER NOT NULL DEFAULT 1
manual                INTEGER NOT NULL DEFAULT 1
created_at            TEXT NOT NULL
updated_at            TEXT NOT NULL
UNIQUE(endpoint_type, url, account_identifier)
```

允许的 `endpoint_type` 仅限：

```text
rss / atom / website / rsshub / rssbridge / account / api / hotlist
```

不得用任意字符串临时扩展类型。新增类型必须同时具备 Adapter、验证、健康状态和迁移方案。

### 4.3 新增 `radar_topic_endpoints`：主题绑定

```text
topic_id       TEXT NOT NULL
endpoint_id    INTEGER NOT NULL
enabled        INTEGER NOT NULL DEFAULT 1
created_at     TEXT NOT NULL
PRIMARY KEY(topic_id, endpoint_id)
```

- 主题选择“全部来源”时，绑定当前所有启用且允许全局使用的端点；
- 后续新增端点是否自动加入“全部来源”主题，必须由明确的 `scope_mode=all` 规则决定；
- 选择“指定来源”时，只处理显式绑定端点；
- 不再使用 `L1/L2/L3` 字符串代替真实端点绑定。

### 4.4 扩展 `source_fetch_states`：运行状态

每个端点对应一条状态，而不是每个关键词对应一条状态：

```text
endpoint_id
etag
last_modified
cursor_value
last_checked_at
last_success_at
next_fetch_at
consecutive_failures
cooldown_until
average_update_seconds
last_http_status
status
item_count
last_error
lease_owner
lease_until
updated_at
```

状态枚举固定为：

```text
unknown / checking / healthy / unchanged / degraded / cooldown / auth_required / disabled
```

## 5. Adapter 契约

所有采集方式必须实现同一最小契约：

```python
class RadarSourceAdapter:
    def validate(endpoint) -> ValidationResult: ...
    def discover(url) -> list[DiscoveredEndpoint]: ...
    def fetch(endpoint, state) -> FetchResult: ...
    def normalize(raw_item, endpoint, captured_at) -> Mention: ...
```

`FetchResult` 至少包含：

```text
status / items / etag / last_modified / cursor_after /
http_status / checked_at / error_code / error_message
```

硬约束：

- `fetch()` 不做关键词查询和 AI 调用；
- `normalize()` 输出必须符合统一 Mention；
- HTTP 304 返回 `unchanged`，不能记为失败；
- 只有完整解析成功后才能提交新游标；
- 错误信息最多保存 500 字符，不保存响应正文和密钥；
- Adapter 单测不得依赖真实互联网，使用固定响应夹具；
- 真实网络测试单独标记，不进入默认离线测试。

## 6. 同步与分发规范

### 6.1 唯一允许的数据流

```text
端点调度 → 获取租约 → 单次抓取 → 规范化 → Mention 幂等入库
        → 查询关联主题 → 本地关键词匹配 → mention_topics 关联
        → 完成运行记录 → 提交 ETag/游标 → 计算下次运行时间
```

### 6.2 RSS/Atom 增量规则

1. 新增端点时先执行检测和预览，用户确认后才保存；
2. 首次同步默认最多导入最近 50 条，可选 20/50/100，不能无限回灌；
3. 请求发送保存的 `If-None-Match` 和 `If-Modified-Since`；
4. 304 只更新检查时间和下次运行时间；
5. 200 响应限制体积、内容类型和解析时间；
6. 按 GUID → 规范化 URL → 来源内内容指纹顺序去重；
7. 发布时间不可信或缺失时使用首次发现时间，并在 UI 明确区分；
8. 同一端点无论关联多少主题，每轮只允许一个外部请求；
9. 同一 Mention 可以关联多个主题，正文和原始元数据只存一份。

### 6.3 调度与并发

- 默认全局并发不超过 4；
- 单主机并发不超过 1；
- 默认间隔 15 分钟，允许范围 5—1440 分钟；
- 连续失败按 30 秒、60 秒、120 秒、300 秒、900 秒退避；
- 达到 5 次连续失败进入冷却，用户可手动测试恢复；
- 多进程/多容器必须使用数据库租约，禁止仅依赖进程内锁；
- 服务重启后从数据库的 `next_fetch_at` 恢复，不重置所有来源立即并发抓取；
- 用户点击“立即同步”必须返回任务状态，不使用固定 1.8 秒等待猜测完成时间。

### 6.4 删除语义

- 删除端点默认只停止未来同步并保留历史 Mention；
- 永久清理历史必须是单独的高风险动作，明确展示数量并二次确认；
- 删除来源身份前必须处理其端点，不允许留下悬空外键；
- 删除主题只删除主题关联和订阅，不删除其他主题共享的 Mention。

## 7. 设置页 UI 规范

设置左侧菜单顺序固定为：

```text
搜索服务 / 分析模型 / 信息来源 / 雷达管理 / 账户管理
```

### 7.1 页面结构

- 页面标题：`雷达管理`；
- 说明：`管理 RSS、网站和公共账号的采集入口与同步状态。`；
- 顶部只保留一个主按钮：`添加信源`；
- 次级操作：`立即同步全部`，使用普通按钮，不与主按钮竞争；
- 使用连续列表和留白组织，不为每个来源创建大圆角卡片；
- 桌面使用列表 + 右侧详情区；移动端使用列表 + 全屏详情页或底部抽屉；
- 不在列表直接显示完整密钥、Cookie 或超长查询参数。

### 7.2 列表字段

```text
名称 / 类型 / 地址或账号 / 关联主题数 / 最近同步 / 下次同步 / 状态 / 启停
```

- 只保留表头分隔线，行通过留白和悬停背景区分；
- 状态使用文字配合低饱和圆点，不能只依赖颜色；
- 地址单行截断，悬停或详情区显示完整值；
- 异常行显示简短原因，完整错误进入详情区；
- 空状态必须引导添加 RSS，不宣称已覆盖全网。

### 7.3 添加流程

固定为三步，不允许把所有字段一次性堆入表单：

1. 选择 `RSS/Atom`、`网站` 或 `公共账号`；
2. 输入地址/平台信息并点击 `检测`；
3. 展示检测结果，选择来源身份、关联主题和更新频率后保存。

保存按钮只有在检测成功后可用。网站发现多个 Feed 时必须让用户选择，不自动全选。

### 7.4 同步反馈

- `立即同步` 返回任务 ID；
- 前端按任务状态轮询：排队、采集中、成功、部分失败、失败；
- 成功后显示新增数、匹配数和来源数；
- “0 条命中”必须区分“成功但无匹配”与“未配置/采集失败”；
- 页面统计中的“来源数”指命中来源数，旁边另显示本轮已检查端点数，避免语义混淆。

## 8. API 边界

```text
GET    /api/radar/sources
POST   /api/radar/sources/discover
POST   /api/radar/sources
GET    /api/radar/sources/<id>
PATCH  /api/radar/sources/<id>
DELETE /api/radar/sources/<id>
POST   /api/radar/sources/<id>/test
POST   /api/radar/sources/<id>/sync
GET    /api/radar/sources/<id>/health

GET    /api/radar/topics/<id>/sources
PUT    /api/radar/topics/<id>/sources

POST   /api/radar/sync
GET    /api/radar/sync/<task_id>
```

约束：

- `discover/test` 不产生持久化修改；
- 创建端点必须通过同一套后端校验，不能信任前端检测结果；
- PATCH 不允许修改端点主类型；类型变化必须新建端点；
- DELETE 默认使用保留历史模式；
- 批量同步必须有幂等任务键和并发租约；
- 所有接口继续使用现有管理员鉴权、请求体限制、速率限制和结构化日志。

## 9. 安全与合规边界

### 9.1 SSRF 防护

- 默认只允许 HTTP/HTTPS；
- 禁止 `file:`、`ftp:`、`data:`、`javascript:` 等协议；
- 默认阻止回环、链路本地、云元数据、多播和未授权私网地址；
- 每次重定向都重新校验目标地址；
- 对 DNS 解析结果再次检查，避免 DNS rebinding；
- 限制重定向次数、响应大小、总耗时和压缩后体积；
- NAS/RSSHub 等内网来源必须通过管理员白名单显式开放，不能全局关闭 SSRF 防护。

### 9.2 凭据

- 不接受账号密码；
- API Token 只保存于现有后端密钥系统或环境变量；
- `auth_ref` 仅保存密钥引用，不保存明文；
- GET 接口不返回密钥；
- 日志、错误、导出和备份清单不得包含明文凭据。

### 9.3 内容边界

- 只采集公开可访问内容；
- 尊重来源条款、robots 和合理请求频率；
- 不主动突破反爬或验证码；
- 默认只保存标题、URL、摘要和时间；正文只在明确功能需要且来源允许时按需获取。

## 11. 验收清单

### 11.1 功能

- [ ] 添加有效 RSS 后可预览 Feed 名称和最近条目；
- [ ] 无效 HTML、登录页、超大响应和非 Feed 内容被拒绝；
- [ ] 同一端点不能重复添加；
- [ ] 一个端点关联多个主题时每轮只请求一次；
- [ ] 修改主题绑定不影响其他主题历史；
- [ ] 删除端点后历史时间线仍可查看；
- [ ] 网站可自动发现 Feed，未发现时展示受控替代方案；
- [ ] 不支持的公共账号明确显示不支持。

### 11.2 同步正确性

- [ ] ETag/Last-Modified 请求和 304 行为正确；
- [ ] 失败不推进游标，成功后原子提交游标；
- [ ] GUID、规范化 URL 和内容指纹去重可复现；
- [ ] 发布时间与首次发现时间不会混淆；
- [ ] 重启后继续使用原状态，不重复回灌历史；
- [ ] 手动同步展示真实任务状态，不使用固定延时猜测；

## 12. 变更控制

以下变化必须先修改本文件并获得人工确认，不能直接开发：

- 引入浏览器自动化作为后台主采集器；
- 保存登录 Cookie、账号密码或个人会话；
- 默认启用付费搜索；
- 引入新的常驻服务、队列或数据库；
- 改变历史 Mention 的删除语义；
- 将雷达与 AI 分析、情绪判断或自动报告合并；
- 开放任意内网 URL 抓取；
- 新增未定义的端点类型或万能抓取器。

任何例外必须记录：业务理由、影响范围、成本、安全风险、替代方案、回滚步骤和新的验收项。
