# 开源项目调研与演进路线图（v0.1）

> 更新：2026-09-02 ｜ 用途：为本项目的后续开发提供可验证的外部参照与取舍依据。
>
> 范围：只吸收与“本地部署、多信源采集、证据可追溯、四段式报告”一致的工程思想；不直接复制第三方实现，也不把受限社媒深度爬取当作默认能力。

---

## 0. 第一性原理：先解决什么问题

舆情系统的交付物不是一段“看起来合理”的 AI 文本，而是**可追溯、可重复、可解释的判断**。因此能力建设顺序必须服从下面的因果链：

```text
可获得且合规的原始证据
  → 统一结构、去重、来源与时间可追溯
  → 可重复的统计/聚类/风险信号
  → AI 基于证据撰写与复核
  → 可恢复的持续监测与去重告警
  → 受控地对外部署
```

任何跳过前两层、直接叠加 Agent、图表或定时任务的做法，都会放大噪声、幻觉与维护成本。当前项目的正确定位是：**单机优先的研究型舆情工作台**，而不是声称覆盖全网的商业爬虫平台。

## 1. GitHub 项目调研与取舍

| 项目 | 值得借鉴 | 不直接照搬 | 对本项目的落点 |
|---|---|---|---|
| [BettaFish / 微舆](https://github.com/dukaworks/betta-fish) | 把搜索、专项分析、报告整合拆成明确角色；多视角可降低单一叙事偏差 | 完整多 Agent 论坛、全平台深爬、多模态链路成本很高，且超出当前数据边界 | 保留现有“事实→原因→风险→对策”固定拓扑；仅新增按条件触发的**证据质量复核**，不引入 LangGraph/论坛机制 |
| [Harken](https://github.com/VladUZH/harken) | 插件化来源、统一 Mention 结构、内容哈希去重、SQLite 本地优先、游标恢复、失败来源不阻断、告警去重 | 其英文社媒适配器和词典不能直接替代中文语义与现有四段式报告 | 建立统一 `mentions / scan_runs / cursors / alerts` 数据模型；先支持增量扫描和持久化基线 |
| [MediaRadar](https://github.com/JAYDEN-LIAO/MediaRadar) | 调度、订阅、熔断、模型回退、鉴权、限流、指标、健康检查的分层完整 | FastAPI + Next.js + Playwright + LangGraph + 多租户体系过重；本机还受“无 C 扩展”约束 | 将其能力拆成轻量阶段：先访问令牌/限流/日志，再 APScheduler，再按需引入多用户与指标 |
| [PublicOpinion](https://github.com/CodeAsPoetry/PublicOpinion) | “采集→清洗→摘要/分类/情感→可视化”的完整传统链路；强调爬取边界与工程拆分 | 旧式模型和大规模分布式栈不适合直接作为当前技术方案 | 明确“规则统计先行、LLM 增强可选”；为离线评测集和人工抽样留出接口 |
| [SearXNG](https://github.com/searxng/searxng) | 多引擎聚合与 JSON 搜索接口 | 公共实例不可视作稳定服务；不同引擎的检索语法/结果能力不一致 | 自建实例为生产主路径；启动时探测 JSON、可用引擎和限流能力，公共实例仅作联调/降级 |

调研日期为 2026-09-02。第三方项目的功能描述和架构均以各自 GitHub README 为准；若要复制任何代码、模型或数据集，必须在实施前单独核验许可证、数据来源、平台条款与个人信息处理义务。

## 2. 目标架构：在现有 Flask + SQLite 上渐进演进

当前架构不需要推倒重来。新增能力应以“适配器 + 统一证据 + 作业状态”围绕现有 `pipeline.py` 生长：

```text
来源适配器（SearXNG / 热榜 / RSS / 未来合规 API）
        ↓ 标准化
Mention（证据记录） ─→ 内容哈希去重 ─→ SQLite / 原始快照
        ↓                              ↓
  统计信号（量级、来源、时间、情感、主题）  ScanRun / Cursor / SourceHealth
        ↓                              ↓
  四段式 AI 流水线 ←── 有来源的精简证据集   订阅 / 阈值 / 去重告警
        ↓
 report.json → 网页 / Markdown / Word / PDF
```

### 2.1 新的最小证据模型（G1）

每一条入库素材统一为 `Mention`，至少应含：

- `id`、`content_hash`、`canonical_url`：幂等与去重；
- `topic_id`、`scan_run_id`、`source_id`、`source_type`：知道“为何、何时、由谁采到”；
- `title`、`snippet`、`body`、`published_at`、`captured_at`：内容与时间；
- `source_name`、`level`、`credibility`、`fetch_status`：证据等级和采集质量；
- `raw_path` 或受控原始响应摘要：可审计、可重跑；
- `engagement`（可选）：热度、评论、转发等平台指标，必须保存原单位与来源。

`report.json` 继续是报告的渲染源，但必须保存所引用的 `mention_id` 或 URL 列表；不能只保留模型生成文本。

### 2.2 来源适配器契约（G2）

每个来源实现同一契约：`capabilities()`、`fetch(query, cursor)`、`normalize(raw)`、`healthcheck()`。能力声明至少包括：是否需要密钥、是否支持增量游标、正文可得性、许可/条款备注、频率上限、可用字段和降级策略。

这样新增 RSS、官方 API 或海外公开社区时只增加适配器和目录数据；平台失效时只影响自身 `SourceHealth`，不应让整次分析失败。

### 2.3 分析质量门（G3）

LLM 不负责替代确定性计算：

- 信源、时间分布、重复率、链接状态、跨来源数量必须由程序计算；
- AI 只对已筛选的证据集做事实编排和解释；
- 对“单源高风险结论、无 S/A 事实锚点、引用 URL 不可达、对策无风险映射”触发低成本复核；
- 复核输出必须返回 `claim / evidence_ids / status / reason`，不能只返回“通过/不通过”。

默认不启用多 Agent 辩论；只有质量门连续发现问题时，才考虑增加一个受预算限制的“审校角色”。

## 3. 分期路线图与验收

### G0：现有闭环的工程收口（最高优先级）

**目标**：先让已写的能力真实、可测、可恢复。

| 子项 | 交付 | 验收 |
|---|---|---|
| G0a 配置一致性 | `config` 改为运行时读取或显式注入；SearXNG、超时、采集组保存后真实生效 | 修改 SearXNG 地址和采集组后，不重启服务跑两次任务，查询日志与设置一致 |
| G0b 进度与任务语义 | 要么接通非流式阶段进度，要么移除“已生成 N 字”的无效承诺；任务取消/失败原因结构化 | 一次成功、一次 AI 失败、一次搜索失败均能显示明确阶段和可操作原因 |
| G0c 缓存与文件安全 | URL 核查按单 URL 当日缓存；报告文件名安全化；临时 docx 文件不冲突 | 同日两主题链接状态互不串用；含 `/ : * ?` 的主题仍可生成三件套 |
| G0d 自动化验证 | 纯 Python 单元测试 + Flask 健康检查冒烟 + 固定素材的 AI 阶段样例 | 无 AI Key、无网络条件下跑完核心测试 |

### G1：统一证据模型与采集可靠性

**目标**：让“采集到什么、为何相信、能否复跑”成为系统能力。

| 子项 | 交付 | 验收 |
|---|---|---|
| G1a Mention/ScanRun/Cursors 表 | 迁移脚本、幂等写入、内容哈希、原始快照索引 | 同一 URL/内容重复采集不重复计数；历史报告仍可预览 |
| G1b 来源适配器与健康度 | SearXNG、热榜、Buzzing 统一契约；`source_health` 状态 | 单一来源 403/改版时，其余来源和报告仍可运行，并记录原因 |
| G1c 检索能力预检 | 启动/任务前探测 SearXNG JSON、引擎、限流和网络延迟 | 不支持 JSON 的实例被标为不可用，不再产生难懂的解析错误 |

### G2：持续监测与风险告警（恢复原 C2 的正确前置）

**目标**：从“单次写报告”升级为“可恢复的周期观察”。

| 子项 | 交付 | 验收 |
|---|---|---|
| G2a 订阅主题 | `topics / subscriptions`，关键词、信源、周期、阈值、启停状态 | 可创建一个主题，重启后仍存在且配置不丢失 |
| G2b 作业与游标 | 单进程 APScheduler；作业互斥、scan run、成功后提交游标 | 中断后重启不会重复发送旧告警；失败作业可安全重试 |
| G2c 信号与告警 | 新增量、声量突增、负面占比变化、S/A 新事实源、链接失效；邮件/Webhook 先二选一 | 同一信号在冷却窗口内只通知一次，测试通知不污染真实记录 |
| G2d 周期报告 | 日报/周报从已持久化 Mention 聚合生成，不重复全网抓取 | 报告可显示时间窗口、样本量、较基线变化和数据局限 |

### G3：安全、可观测性与交付

**目标**：具备可控外部部署条件。

| 子项 | 交付 | 验收 |
|---|---|---|
| G3a 安全基线 | 首次启动管理员 token、设置接口鉴权、密钥永不回传、请求体上限、限流、受限 CORS、安全响应头 | 未带 token 不能读取/修改设置和报告编辑；浏览器网络面板中不出现 API Key |
| G3b 结构化日志与指标 | `scan_run_id` 贯穿日志；来源成功率、耗时、去重率、AI 调用/失败率、告警数 | 发生失败时可在一次查询中定位任务、来源和 AI 通道 |
| G3c 部署交付 | A1b compose（含可选 SearXNG）、备份/恢复、升级/回滚、健康检查 | 新机器按文档部署并从备份恢复 SQLite 与报告 |

### G4：分析增强（最后实施）

- 主题聚类、事件演化、立场/受众分层；
- 国际舆情模板和合规海外公开源；
- 有评测集和质量门数据后，再评估轻量“审校 Agent”；
- 多用户、配额、复杂推送通道仅在明确产品需要后立项。

## 4. 明确不做或暂缓做

1. 不绕过登录、验证码、反爬机制，也不承诺获取私域、付费或受限平台评论。
2. 不在证据未持久化前实现定时抓取和自动告警。
3. 不为“看起来先进”引入 LangGraph、Redis、消息队列、向量库或微服务；出现单机 SQLite/后台线程的明确瓶颈后再评估。
4. 不把模型情感百分比当作精确民调；所有情感/趋势都必须显示样本量、时间窗和信源范围。
5. 不把公共 SearXNG 实例当作生产依赖；生产必须准备自建实例或清晰的降级状态。

---

## 5. 每次接手的执行顺序

1. 阅读 `docs/开发手册.md` 的进度表、待验证、最近提交和本文件的当前阶段。
2. 先确认任务是否已有 `✅✅` 的验收记录；没有就补验证，不跳到后续阶段。
3. 任何涉及采集或 AI 的改动，均同时验证：正常、单来源失败、AI 不可用三条路径。
4. 任何涉及存储的改动，均提供向前兼容迁移和重启后验证。
5. 完成一个子步骤就同步开发手册、验收记录和里程碑；不要把规划当作实现完成。
