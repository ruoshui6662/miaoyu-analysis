## 1. 功能目标

「雷达」用于持续回答一个简单问题：**最近有哪些公开新闻提到了用户关心的关键词？**

用户可以创建多个监测主题，每个主题包含主关键词、别名和排除词。系统周期性获取公开新闻，将命中的内容保存为可追溯记录，并按时间线呈现。

雷达与“分析”必须保持清晰边界：

- 雷达负责发现、记录、去重、排序和原文跳转；
- 分析负责基于用户选定主题生成事实、原因、风险与建议；
- 雷达页面不展示情绪、热度结论、风险等级、AI 摘要或对策；
- 用户可以从雷达中的一条新闻进入“分析”，但不会自动启动付费分析。

### 1.1 导航位置

顶部导航固定为：

```text
首页 → 分析 → 雷达 → 历史 → 设置
```

“雷达”位于“分析”和“历史”之间，与现有导航保持同级，不放入设置页或首页二级区域。

### 1.2 默认使用流程

1. 用户进入雷达，首次使用时看到创建关键词引导。
2. 用户填写主题名称、关键词/别名、排除词、监测频率和可选信源范围。
3. 保存后立即执行一次轻量扫描，以后由后台自动更新。
4. 左侧关键词显示启用状态、未读数量和最近更新时间。
5. 用户选择一个关键词，右侧按“今天/昨天/更早”查看新闻时间线。
6. 用户可以筛选时间和来源、手动刷新、打开原文或将某条新闻带入分析页。

## 2. 第一性原理与核心架构

持续监测的成本不应随“关键词数 × 新闻源数”线性放大。正确模型是：**先按信源统一采集一次，再在本地匹配全部关键词。**

```text
信源调度器
  → 每个信源只抓取一次增量内容
  → 统一标准化 Article/Mention
  → 本地匹配所有启用关键词
  → URL 指纹与标题近似去重
  → 关联到一个或多个主题
  → SQLite 持久化
  → 时间线 API
  → 雷达页面
```

复杂度目标从：

```text
O(关键词数 × 信源数 × 每次请求)
```

降低为：

```text
O(信源数 × 增量请求) + O(新增条目 × 关键词匹配)
```

本项目关键词规模预期为几十个，直接使用规范化字符串和正则匹配即可；不引入向量库、搜索集群或重型消息队列。

### 2.1 不直接复用分析采集器

现有 `collector.collect_topic()` 面向一次性深度分析：每次主题扫描会按多个搜索组和多个关键词发起请求，并尝试抓取正文。它不适合高频雷达。

雷达必须新增轻量采集路径，遵守以下约束：

- 默认只采集标题、URL、摘要、来源、发布时间和首次发现时间；
- 不在每轮扫描中下载正文；
- 只有标题/摘要无法确定是否命中，或用户打开详情时，才按需抓取正文；
- 不调用 `evaluate_topic()`，不生成风险、情感、热度和周期报告；
- 现有事件归并只能用于折叠重复报道，不在雷达中展示热度分数。

## 3. 六层信息获取架构

六层架构同时定义采集优先级、展示代表来源优先级和失败降级顺序。它不是每轮扫描都逐层调用的瀑布链路。

### 第 1 层：媒体与机构官方 RSS/Atom

**定位**：默认主链路，成本最低、时间字段最可靠。

- 优先使用媒体、政府机构和专业站点自行提供的 RSS/Atom；
- 每个源保存 `ETag`、`Last-Modified` 和最近成功时间；
- 支持 HTTP 304，未变化时不重复下载和解析；
- 初始间隔 10 分钟，根据过去 7 天更新频率在 5—60 分钟内自适应；
- 单主机并发不超过 1，全局采集并发默认不超过 4。

### 第 2 层：NewsNow 与项目已有公开聚合/热榜源

**定位**：补充中文实时热点，不承担任意关键词的完整覆盖。

- 复用现有 NewsNow、Buzzing 和启用的公开 Feed；
- 复用现有全局缓存，禁止每个关键词重复请求同一榜单；
- 获取后在本地匹配全部关键词；
- 热榜原始排名只作为来源元数据，不在雷达中转换为统一热度。

### 第 3 层：RSSHub / RSS-Bridge

**定位**：为没有官方 Feed 的已知新闻站点补齐结构化更新。

- 作为可配置外部服务，不在 MVP 中把完整项目打包进妙舆镜像；
- 设置中预留 `RSSHUB_BASE_URL`、`RSS_BRIDGE_BASE_URL`；
- 单条路由失效只标记该源异常，不影响其他来源；
- 路由连续失败达到阈值后进入冷却，并提示管理员检查页面改版；
- RSSHub 采用 AGPL-3.0，引入或修改前需单独做许可证合规检查；RSS-Bridge 仍需核对具体 Bridge 抓取目标的使用条款。

### 第 4 层：自建 SearXNG 定时补漏

**定位**：扩大覆盖，不承担分钟级主采集。

- 默认每个主题 2—6 小时执行一次补漏搜索；
- 请求使用 `categories=news`，优先 `time_range=day`；
- 主题中的主关键词和别名按预算分批查询，不在每轮重复搜索全部词；
- 使用现有 `SearchRouter`，但雷达默认只允许 SearXNG，不自动进入付费 Provider；
- SearXNG 未配置或 JSON API 不可用时跳过，并在来源健康状态中说明原因。

### 第 5 层：GDELT 全球新闻补充

**定位**：补充海外和跨语言公开新闻，默认可关闭。

- 使用 GDELT DOC API 的时间窗和文章列表输出；
- 适用于国际人物、企业和跨境事件；
- 结果必须经过语言、时间、标题/摘要关键词和域名过滤；
- 不把 GDELT 的机器翻译或相关性排序作为事实判断；
- 中文本地新闻噪声较高时自动降低调用频率，不阻塞主链路。

### 第 6 层：Brave Search / Tavily 付费兜底

**定位**：只有明确触发条件时使用，默认不参与后台高频轮询。

允许触发的条件：

1. 用户主动点击“立即刷新”并选择“扩大搜索范围”；
2. 第 1—5 层连续异常，且管理员已经配置 API Key 和月度预算；
3. 定时完整性校验发现某主题长时间没有任何结果，且该主题仍为启用状态。

约束：

- 默认使用 `failover`，不执行 Brave 与 Tavily 并行多源合并；
- Tavily 使用 basic search，关闭 answer、raw content 和图片；
- Brave/Tavily 每日和每月请求额度必须可配置；
- 达到预算后停止调用并显示“付费补漏额度已达上限”，不得静默扣费；
- 雷达会持久化标题、链接和摘要，启用 Brave 前必须核对所选套餐的数据存储权利。

### 3.1 调度策略总结

| 层级 | 默认行为 | 建议频率 | API 费用 |
|---|---|---:|---:|
| 1 官方 RSS | 持续增量采集 | 5—60 分钟自适应 | 0 |
| 2 公开聚合/热榜 | 持续复用全局缓存 | 5—15 分钟 | 0 |
| 3 RSSHub/Bridge | 按已配置路由采集 | 10—30 分钟 | 自建资源 |
| 4 SearXNG | 定时查漏 | 每主题 2—6 小时 | 当前边际成本 0 |
| 5 GDELT | 可选海外补充 | 30—120 分钟 | 0 |
| 6 Brave/Tavily | 条件触发兜底 | 手动或每日完整性检查 | 按量计费 |

默认部署目标是**不配置任何付费 Key 也能工作**，因此雷达的默认 API 费用应为 0。

## 4. 关键词匹配规则

### 4.1 主题字段

每个主题至少包含：

- `name`：左侧显示名称；
- `keywords`：主关键词和别名，任意一个命中即关联；
- `exclude_keywords`：命中任意排除词则不关联；
- `enabled`：是否继续监测；
- `interval_seconds`：用户看到的更新频率，不低于系统最小值；
- `source_scope`：全部来源或用户限定来源；
- `last_read_at`：用于计算左侧未读数量。

示例：

```json
{
  "name": "小米汽车",
  "keywords": ["小米汽车", "SU7", "YU7", "雷军汽车"],
  "exclude_keywords": ["模型玩具", "壁纸"],
  "source_scope": ["all"],
  "interval_seconds": 900,
  "enabled": true
}
```

### 4.2 匹配顺序

1. 对标题、摘要和关键词执行 Unicode NFKC、大小写、空白和常见标点规范化。
2. 标题命中主词或别名：直接收录。
3. 标题未命中但摘要命中：收录并标记 `match_location=snippet`。
4. 标题/摘要未命中：默认不抓正文；只有按需补充任务才能进入正文确认。
5. 命中排除词：拒绝关联，并在扫描日志中累计过滤数量。
6. 一条新闻可以关联多个主题，但底层 Mention 只存一份。

MVP 不做语义向量或 LLM 相关性判断，避免“有关”被不可解释地扩大。后续只有真实漏报样本证明规则匹配不足时，再评估可选语义匹配。

## 5. 增量、去重与时间语义

### 5.1 增量状态

每个信源独立维护：

- `etag`、`last_modified`；
- `cursor_value`；
- `last_success_at`、`next_fetch_at`；
- `consecutive_failures`、`cooldown_until`；
- `average_update_seconds`；
- `last_error`（最多保留 500 字符，不含密钥和响应正文）。

只有一次采集完整成功后才推进游标。失败时保留原游标，并按 30 秒、60 秒、120 秒、300 秒、900 秒退避，叠加少量随机抖动，防止所有来源同时重试。

### 5.2 去重规则

按以下顺序处理：

1. 规范化 URL 完全一致：同一 Mention；
2. 来源 GUID 一致：同一 Mention；
3. 同一主题、72 小时内标题规范化完全一致：折叠；
4. 标题二元组相似度达到阈值：标记为候选重复，但保留来源关系；
5. 多来源重复报道在 UI 中显示“另有 N 个来源报道”，默认代表条目优先选择更高层级、发布时间更早且字段更完整的来源。

不得因标题近似就删除底层证据；折叠只是展示策略。

### 5.3 时间字段

- 数据库统一保存 UTC ISO 8601；
- UI 按浏览器本地时区展示；
- 排序优先使用可信 `published_at`，缺失或异常时使用 `first_seen_at`；
- 页面必须区分“发布时间”和“发现时间”，不能把抓取时间伪装为媒体发布时间；
- 同一条新闻重复采集只更新 `last_seen_at`，不改变 `first_seen_at`。

## 6. 数据模型规划

优先复用现有 SQLite 表：

- `topics`：关键词主题；
- `subscriptions`：周期、启停和重试；
- `mentions`：新闻事实记录；
- `mention_topics`：一条新闻与多个主题的关联；
- `monitor_runs`：每次扫描状态；
- `cursors`：现有简单游标兼容层。

建议迁移：

### 6.1 `topics` 扩展

```text
kind              TEXT DEFAULT 'radar'
source_scope_json TEXT DEFAULT '["all"]'
last_read_at      TEXT DEFAULT ''
```

`keywords_json` 继续同时保存主词和别名，不新增重复的 aliases 表。

### 6.2 `mention_topics` 扩展

```text
matched_keywords_json TEXT DEFAULT '[]'
match_location        TEXT DEFAULT 'title'
```

### 6.3 新增 `source_fetch_states`

```text
source_id                 TEXT PRIMARY KEY
etag                      TEXT DEFAULT ''
last_modified             TEXT DEFAULT ''
cursor_value              TEXT DEFAULT ''
last_success_at           TEXT DEFAULT ''
next_fetch_at             TEXT DEFAULT ''
consecutive_failures      INTEGER DEFAULT 0
cooldown_until            TEXT DEFAULT ''
average_update_seconds    INTEGER DEFAULT 0
last_error                TEXT DEFAULT ''
updated_at                TEXT DEFAULT ''
```

迁移必须向前兼容；已有 `topics/subscriptions/mentions` 数据不能丢失，旧监测与周期报告接口继续可用。

## 7. API 规划

对外使用 `/api/radar/*`，内部可以复用 `/api/monitor/*` 的服务函数，但不能让前端依赖内部 G2 告警接口。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/radar/topics` | 关键词列表、未读数、状态和最近更新 |
| POST | `/api/radar/topics` | 创建主题并触发首次扫描 |
| PATCH | `/api/radar/topics/<id>` | 修改名称、关键词、排除词、周期、来源和启停 |
| DELETE | `/api/radar/topics/<id>` | 删除订阅；历史新闻采用保留或清理的显式参数 |
| POST | `/api/radar/topics/<id>/refresh` | 手动刷新；默认免费链路，可选扩大搜索范围 |
| POST | `/api/radar/topics/<id>/read` | 更新主题最后阅读时间 |
| GET | `/api/radar/timeline` | 获取单主题时间线，使用 cursor 分页 |
| GET | `/api/radar/source-health` | 返回六层信源状态和下一次更新时间 |

时间线请求示例：

```text
GET /api/radar/timeline?topic_id=abc123&range=7d&source=all&limit=30&before=<cursor>
```

响应条目至少包含：

```json
{
  "id": 123,
  "title": "新闻标题",
  "snippet": "来源原始摘要",
  "url": "https://example.com/article",
  "source_id": "新华社",
  "source_layer": 1,
  "published_at": "2026-09-05T07:42:00Z",
  "first_seen_at": "2026-09-05T07:44:12Z",
  "matched_keywords": ["郑钦文"],
  "match_location": "title",
  "duplicate_source_count": 3
}
```

列表分页必须使用时间+ID cursor，不使用不断变动的页码，避免新内容插入后重复或漏读。

## 8. 已确认 UI 规范（图一）

### 8.1 桌面布局

- 页面使用当前冷白底、白色工作面和妙舆红；不新增暖灰背景；
- 顶部导航保持现有高度和激活下划线；
- 内容区为左窄右宽两栏，左栏建议 216—240px，右栏 `min-width: 0`；
- 左右区域通过空间和极弱分隔组织，不套大型圆角外卡；
- 页面最多一个实心红色主动作“添加关键词”；“立即刷新”为中性次操作；
- 普通按钮桌面高 40px，图标 16px；不得为主动作单独放大高度。

### 8.2 左侧关键词栏

顺序固定为：

1. 搜索关键词；
2. 关键词列表；
3. 当前状态与未读数；
4. 底部简短说明或排序入口。

关键词行展示名称、启用状态和未读数。选中行使用左侧 2px 红色标记和极浅红背景；未选中行无边框、无阴影。支持键盘上下选择，拖动排序作为后续增强，不阻塞 MVP。

### 8.3 右侧时间线

顶部顺序固定为：

1. 当前关键词标题；
2. 时间、来源和媒体类型筛选；
3. 最近更新时间和来源健康状态；
4. 按“今天/昨天/具体日期”分组的新闻列表。

每行固定信息层级：

```text
时间 → 来源 Logo → 标题 → 原始摘要
                         → 来源名 / 发布时间 / 命中词
```

- 行不是独立卡片；依靠列对齐、24px 左右的垂直留白和悬停底色建立边界；
- 日期组之间允许一条极弱分隔线，普通行不使用贯穿式横线；
- 来源 Logo 使用现有本地图标库和统一槽位；加载失败回退为来源类别图标；
- 标题最多两行，摘要桌面最多两行，不能挤压来源和时间列；
- 点击标题打开原文；“带入分析”只在悬停、聚焦或详情菜单中出现，不形成连续红色按钮；
- 重复来源折叠为“另有 N 个来源报道”，展开后仍按时间排列。

### 8.4 移动端

- 左侧栏变为页面顶部的横向关键词切换区或抽屉，不与时间线并排；
- 顶部只保留当前主题、添加和筛选三个核心入口；
- 时间、Logo、标题为主列，来源和发布时间下沉到元信息行；
- 按钮视觉尺寸保持紧凑，触控热区不小于 44px；不把所有操作放大为全宽按钮；
- 360/390/430px 不允许页面级横向溢出；关键词横向区可以局部滚动并隐藏视觉滚动条。

### 8.5 页面状态

必须设计并实现：

- 首次使用：说明功能并提供“添加第一个关键词”；
- 正在首次扫描：显示真实阶段，不显示虚构百分比；
- 暂无结果：说明已检查的时间范围和来源，不暗示系统故障；
- 部分来源异常：时间线继续可用，在状态区显示“5/6 正常”；
- 全部来源不可用：保留历史内容，并提供检查设置和重试入口；
- 付费额度停止：只影响第 6 层，前五层继续工作。

## 9. 稳定性、成本与安全约束

### 9.1 稳定性

- 调度任务必须互斥，同一信源和同一主题不能并发重复执行；
- 每个来源独立失败、独立退避、独立恢复；
- 查询窗口保留 1—2 小时重叠，依靠幂等写入消除重复，降低时间边界漏报；
- 进程重启后从数据库恢复下一次执行时间、游标和失败状态；
- 手动刷新同主题默认 60 秒限流；
- 来源响应超过体积上限、非文本内容或重定向异常时立即停止处理；
- 所有外部请求使用统一 User-Agent、超时和域名安全检查，禁止访问环回和私有地址，避免 SSRF。

### 9.2 成本预算

- 默认不调用 LLM；
- 默认不调用 Brave/Tavily；
- 正文抓取目标小于新增条目的 10%；
- SearXNG 按主题分时调度，避免整点同时请求；
- 第 6 层必须有每日/月度请求上限、剩余额度提示和总开关；
- 日志记录各层请求数、命中数、去重数和失败数，但不记录 API Key。

### 9.3 数据保留

- 默认保留 90 天 Mention 和关联记录；
- 用户收藏或已进入分析的新闻不自动清理；
- 删除主题默认删除主题关联，不直接删除被其他主题或报告引用的 Mention；
- 页面只保存公开新闻的必要元数据和受控摘要，不复制整篇受版权保护正文。

## 11. 验收标准

### 11.1 功能

- [ ] 导航顺序为“首页/分析/雷达/历史/设置”；
- [ ] 可创建、编辑、暂停、恢复和删除多个关键词主题；
- [ ] 一条新闻可同时关联多个主题，底层只保存一次；
- [ ] 时间线支持时间、来源筛选和 cursor 分页；
- [ ] 新闻可打开原文，可选择带入分析，但不会自动分析；
- [ ] 页面不出现情感、风险、热度结论或 AI 生成摘要。

### 11.2 数据正确性

- [ ] 标题和摘要命中规则、排除词规则有单元测试；
- [ ] URL 规范化、GUID、标题近似去重有固定样例；
- [ ] `published_at` 缺失时明确回退到 `first_seen_at`；
- [ ] 重复扫描不增加重复 Mention，不重置首次发现时间；
- [ ] 来源层级只用于采集/代表来源选择，不改变时间线的时间顺序。

### 11.3 稳定与成本

- [ ] RSS 支持 ETag/Last-Modified 和 304；
- [ ] 单源 403、429、5xx、超时不会阻断其他来源；
- [ ] 服务重启后主题、游标、未读状态和任务时间不丢失；
- [ ] 默认未配置 Brave/Tavily 时功能完整可用；
- [ ] 未主动扩大搜索范围时，后台不会调用第 6 层；
- [ ] 达到预算上限后不再产生付费请求；
- [ ] 多关键词场景验证“每个 Feed 每轮只请求一次”。

### 11.4 UI

- [ ] 桌面采用左关键词栏、右时间线，与确认的图一一致；
- [ ] 普通新闻行无独立圆角卡片和阴影；
- [ ] 添加/刷新/筛选控件尺寸遵守现有 UI 规范；
- [ ] 360—1440px 无页面级横向溢出、文字裁切或按钮异常放大；
- [ ] 键盘可操作关键词、筛选、新闻链接和折叠来源；
- [ ] 加载、空数据、部分失败、全部失败和额度停止状态均可辨识。

## 12. 明确不做

1. 不用 AI 判断新闻是否正面、负面或是否存在风险。
2. 不生成日报、周报或自动研判结论；已有周期报告能力保持独立。
3. 不绕过验证码、登录、反爬或付费墙。
4. 不承诺覆盖“全网”，页面只声明当前启用且健康的来源范围。
5. 不把 Brave/Tavily 作为默认持续监控主链路。
6. 不在 MVP 引入 Redis、Celery、Elasticsearch、向量数据库或独立 Miniflux 服务。

## 13. 调研依据

- [RSSHub](https://github.com/DIYgod/RSSHub)：大量站点路由和自建 RSS 能力；作为第 3 层可选外部服务。
- [RSS-Bridge](https://github.com/RSS-Bridge/rss-bridge)：为缺少 Feed 的网站生成 RSS，并提供缓存。
- [NewsNow](https://github.com/ourongxing/newsnow)：公开热点聚合、缓存和自适应抓取思路；项目当前已有接入。
- [SearXNG Search API](https://github.com/searxng/searxng/blob/master/docs/dev/search_api.rst)：JSON/RSS 输出、分类、分页和时间范围。
- [feedparser HTTP ETag](https://feedparser.readthedocs.io/en/stable/http-etag.html)：使用 ETag/Last-Modified 避免重复下载。
- [Miniflux](https://github.com/miniflux/v2)：Feed 增量请求、轮询策略和错误控制的工程参考，不作为 MVP 依赖。
- [GDELT DOC 2.0](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/)：全球新闻全文检索与 JSON 输出。
- [Huginn](https://github.com/huginn/huginn)：事件生产、消费和自动任务的架构参考，不引入其完整运行时。
- [changedetection.io](https://github.com/dgtlmoon/changedetection.io)：已知页面变更监测参考；不适合作为关键词新闻发现主链路。
- [Trafilatura](https://github.com/adbar/trafilatura)：正文与元数据抽取备选；MVP 默认不抓正文，因此暂不引入。
